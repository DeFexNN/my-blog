Atomizer — Writeup

Challenge Overview

This binary is essentially a shellcode loader.
Instead of exploiting a memory corruption bug, the program intentionally gives us executable memory and jumps to whatever we place inside it.

The challenge title and hint:

“I hate it when something is not exactly the way I want it. So I just throw it away.”
“Too much or too little and it won’t spray.”

Both point toward strict input size requirements.

Vulnerability

The program does the following:

1. Allocates RWX memory

Permissions 7 =

So we get memory that is:

✅ writable
✅ executable
✅ at a fixed address

No ASLR guessing needed.

2. Reads user input into that memory

The loop continues until:

If fewer bytes are sent → the program exits.

If exactly 69 bytes are sent → execution jumps directly to our buffer.

Root Cause

The vulnerability is straightforward:

User-controlled data is executed as code without validation.

This is the textbook definition of arbitrary code execution.

There is:

  • no bounds check problem
  • no stack overflow
  • no ROP required

The binary is deliberately designed to run shellcode.

The only constraint is:

⚠️ You MUST send exactly 69 bytes.

Not 68.
Not 70.
Exactly.

Otherwise the program “throws it away.”

Exploitation Strategy

At first glance, spawning /bin/sh seems like the obvious move.

However, modern CTF infrastructure often removes shells or blocks them.

When execve("/bin/sh") fails:

👉 the process exits
👉 the socket closes
👉 you get EOF

So the reliable strategy is:

Use ORW shellcode (Open → Read → Write)

Instead of spawning a shell, just read the flag directly.

Since the mmap’d region is writable, it doubles as our buffer.

After writing the shellcode, we simply pad with NOPs until we hit 69 bytes.
