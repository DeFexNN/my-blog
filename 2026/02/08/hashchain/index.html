6. Why This Works

This challenge is a textbook example of W^X violation — memory is both writable and executable.

Key mistakes:

  • Executable memory created with mmap(..., PROT_READ | PROT_WRITE | PROT_EXEC)
  • User-controlled bytes placed directly into that memory
  • Hash output trusted as safe data
  • A giant NOP sled leading to a privileged function

No collision attack was required. No shellcode was required.

We simply turned MD5 into an instruction generator.

7. Conclusion

The challenge highlights an important lesson:

Cryptographic hashes are not inherently safe — they are just bytes.

If those bytes are ever executed, the hash function becomes irrelevant; the program effectively hands the attacker control of the instruction pointer.

Proper mitigations include:

  • Enforcing W^X (Write XOR Execute) memory protections
  • Never executing derived data
  • Using control-flow protections (CFI)
  • Avoiding RWX mappings entirely
